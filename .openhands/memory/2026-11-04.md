What was learned, in case it is ever asked for again (it is real, and it is
free):
- **Flow Music cannot clone a voice.** It rejects an uploaded clip that has
  vocals ("remove the vocals"); its "Create a similar original track" throws the
  reference away. Proven by test, not assumed.
- The free route is stem swap + **kNN-VC** (bshall/knn-vc, WavLM+HiFi-GAN, CPU,
  zero-shot): pull the clip's vocal stem (`GET /__api/stems/clip/<id>`), convert,
  mix over drums+bass+other. Pitch matched (F0 113-118 Hz vs K's 112).
- It still sounded wrong to K. The 16 kHz vocoder is the ceiling: it strips
  everything above 8 kHz, so breath and sibilance are gone. The "air blend"
  trick (mix the source singer's >6.5 kHz band under the converted vocal) helps
  but does not fix it. A sung vocal at usable quality is probably not reachable
  from kNN-VC on CPU.
- kNN-VC gotchas that cost real time: pass `device="cpu"` to `torch.hub.load`;
  monkey-patch `torchaudio.load/save` to `soundfile` (2.11 wants torchcodec);
  encode in ~15 s chunks or WavLM OOMs and **kills the pod**; keep the reference
  ≤60 s.
- The pod was replaced once mid-task (all desktop apt packages gone) — rebuild
  the desktop with `.agents/skills/ax-cloud-desktop/scripts/bootstrap.py`.
- The vendored ffmpeg was broken (missing `libav*.so`); replaced with the

## 09:45Z — K's bookmarks were lost by my own restore; fixed for good

K reported "รายการโปรดก็หายหมด" (all bookmarks gone). Cause was mine: I ran
`login_vault.py restore-bookmarks` while Chromium was **up**, and the *file* write
it does is silently discarded by Chrome. Two independent reasons it fails:

- Chrome reads `Bookmarks` at profile load and rewrites it on exit, so a write to
  a running browser is clobbered (the docstring even said so — I ignored it).
- Even with Chrome down, the hand-written file is rejected: Chrome verifies a
  top-level `checksum` (an MD5 over the tree) and drops the file when it cannot
  reproduce it. Tried 8+ checksum variants (id/title/url, utf8/utf16, root node
  included or not) — none matched the 32-hex value Chrome writes, so the file route
  is a dead end. Confirmed by test: after a file write + Chrome start the bar was
  empty again.

**The fix (real, tested):** restore through Chrome's own API over CDP —
`chrome.bookmarks.getChildren('1')` then `chrome.bookmarks.create(...)` on
`chrome://bookmarks/`. Chrome then owns the write and the bar survives the next
start. Verified end-to-end: wiped the bar, restored via CDP, killed+restarted
Chromium, bar still had all 9.

- `ops/login_vault.py`: new `restore_bookmarks_via_cdp()`; `restore_bookmarks()`
  prefers it and falls back to the file only when no browser is reachable.
- `.agents/skills/ax-cloud-desktop/scripts/bootstrap.py`: `restore_bookmarks()` now
  runs **after** Chromium is up (was before, which is why the file write got
  clobbered); added `show_bookmark_bar()` (sets `bookmark_bar.show_on_all_tabs=true`
  *before* Chrome starts, since Chrome rewrites Preferences on exit); added the
  missing `import json`; gated the bookmark restore on `OPENHANDS_API_KEY` like
  login.
- The bar was *also* hidden on the new-tab page by Chrome's default, so even a
  good restore looks empty. `show_on_all_tabs` fixes that.
