## The diagnosis (measured + confirmed by 9/10 advisors)
The catalogue was monochrome, not badly written:
- 20/22 songs had **no `# GENRE:` header** → all fell back to one "เพื่อชีวิต"
  style. Only 21 (lukthung) and 24 (rock) were tagged.
- 21/22 **female** voice; tempo clustered **64–96** (mean 79).
- Every song: identical `V-C-V-C-B-C`, ~8 syllables/line, AABB rhyme, and the
  hook sung only **once per chorus** (in-chorus repeat = 1 for 21/22).
- chorus share 0.18, distinct-line ratio 0.64.

The advisor panel (chatgpt, 7 Duck models) all said the same thing: the problem
is **one production template across the whole catalogue**. Recommended fix:
rotate genres (lukthung/rock/pop/indie, none adjacent), spread tempo, vary the
voice, make the arrangement carry identity, use pentatonic as the melodic core.

## The release rail was silently shipping videos with no art (2026-11-06, late)
- **Root cause: the cron ran before the quota reset.** YouTube's daily quotas reset
  at midnight *Pacific* — 07:00 UTC under PDT but 08:00 UTC under PST — and
  `ax-music-release.yml` fired at `0 7,13,19`. In November the 07:00 tick is an
  hour early, so the day's pool was already spent by the time the run landed
  (14:43 UTC on 2026-11-06) and the first `playlistItems.insert` returned 403.
  Moved to `0 9,15,21`.
- **Why nothing failed:** `videos.insert` has its *own* 100/day bucket, separate
  from the shared 10,000-unit pool (Google's quota doc says so explicitly). So all
  six uploads returned HTTP 200 while `thumbnails.set`, `playlistItems.insert` and
  `playlists.insert` all 403'd. A fully green run, six videos with YouTube's
  auto-frame, none in a playlist.
- **`daily_release.py` writes the ledger back only after a successful release**,
  and `release.py` returns 3 when the slots are spent — so the driver returns
  before its write-back. Any repair recorded only in the working copy was lost
  with the job and repeated every run. `fix_thumbnails.py` now writes the ledger
  itself through the Contents API.
- **`playlistItems.insert` is not idempotent** — inserting twice leaves two
  identical rows — so a repair must `in_playlist()` first (1 unit vs 50).
- **A Short's vertical art lives under the song slug** (`thumb-short-song-<slug>.png`),
  not the variant name; the repair was falling back to the square song cover,
  which is the wrong shape for a 9:16 Short, and doing it silently.
- **The heartbeat only read run conclusions**, so a green run hid the defect.
  It now reads `thumb_ok`/`playlist_ok` from the committed ledger and alerts
  while a repair is pending; an unreadable ledger counts as 0 so a hiccup does
  not page the phone.

- Still pending: the 5 flagged releases (4 Shorts + song 06) wait for the next
  fresh Pacific day; `fix_thumbnails.py --ch ch3` is the command.
