was not the code I had been polishing — it was two environment/infra gaps.

**1. A missing `numpy` turned into "retired engine" skips.** `release.py` calls
`provenance.verdict()` to refuse songs rebuilt by the rejected Piper engine. That
module imports numpy. On a fresh pod numpy was absent, the import raised, and

release. That is the actual gap between "rendered" and "queued".

## Clip gate: the ad-hoc mux was the real bug (14/14 now)
`/tmp/qcclip/gemini-qc-proof.mp4` FAILED 12/14 twice for reasons that were *not* in the segment builder:
1. **`picture is not frozen` median 0.0, 939/1241 duplicate frames.** The per-segment Ken Burns zoom was
   fine (segments measured 0.2-0.375), but the final concat+mux was an unsaved ad-hoc command that
   stream-copied across segments with differing timebases, duplicating frames. Fix: concat by
   **re-encoding** (`-vf fps=30,format=yuv420p`), never stream-copy.
2. **`audio aac 48k` FAILED at 96000 Hz** — the narration sources were concatenated without pinning
   `-ar 48000`, and the mux copied that through.
3. Frame rate landed 29.952 (FAIL, rule wants exact profile fps) because the video stream was copied into
   the mux; fix = encode with `-vf fps=30 -r 30 -fps_mode cfr`. Note `-vsync cfr` now errors (exit 8) on
   this ffmpeg build; use `-fps_mode`.
Lesson: **a build step that only exists in shell history is not reproducible and will silently ship a
broken artifact.** `/tmp/qcclip/assemble.py` now owns concat + two-pass loudnorm + mux.

instead of our art. Ran `music938-1/scripts/fix_thumbnails.py` while the shared pool was fresh

1. **`thumb_standard.assert_ok` raises `SystemExit`.** It fires inside `set_thumbnail`, escaped the loop,

   the same mis-scale is on covers 25/27/29/48. Cropped 26 to 1365x768 (10/10). The square 1280x1280

## The thumbnail 429 is a per-account upload window, not the API pool
Probed the raw response: `HTTP 429 reason=uploadRateLimitExceeded domain=youtube.thumbnail
"The user has uploaded too many thumbnails recently."` So it is **not** the shared

## Lyric quality: two measured dead ends (commit 0c848be)

The 42-49 pack shipped as syllable salad — real Thai syllables in no grammatical
order ("บวยบอยในใจทำไมดี", "ฝันบีบไหม้ไปดอกไม้ซุ่มดา"). **All eight passed every
structural check** (line lengths, no Latin, no chrome). Two cheaper gates were
tried and both measured useless, so do not re-derive them:

- **Dictionary coverage is blind to word order.** `thai_words` coverage scored
  **1.00 on the worst lines** — every token is a genuine Thai word. A salad is
  not misspelled, it is ungrammatical.
- **A function-word count is backwards.** Measured per line: salad
  "บวยบอยในใจทำไมดี" = **2.00**; correct "เดินผ่านคืนนี้เงียบงัน" = **0.00**.
  Imagery-only lines are legitimate and carry no function word, so this
  heuristic rejects good lyrics and passes bad ones. I wrote it, measured it,
  and deleted it.

Only a reader of the language can tell → `ai_lyrics.verify_meaning()` asks a
model and believes the answer. It lives in `draft()` (not just `main()`) because
`produce_loop`/`forge_song` call `draft()`; gating the CLI alone leaves the rail
free to render a salad. `repair_lines()` then rewrites only the named line and
re-verifies — one weak line costs that line, not the hook and two verses.

**The Gemini web driver has a Thai UI here.** `parse_body` must cut on
"Gemini บอกว่า" and stop at "Gemini เป็น AI"/"อัปเกรด"/"อัตโนมัติ". Without the
cut the echoed *prompt* survived and its example lyric became the answer's first
verse (the answer looked like it copied the example — it had). Without the stop,
"อัปเกรด" was sung.

**Reader choice matters.** `_drive_gemini` (the lyric driver) waits for

never returns and hands back the page sidebar ("Gemini แชทใหม่ คลัง..."). Use
