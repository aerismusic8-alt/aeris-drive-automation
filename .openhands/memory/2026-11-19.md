# 2026-11-19

## The pipeline was silently publishing NOTHING for a day (two stacked blockers)
K asked twice for status. The honest answer was "nothing new shipped", and the cause
was not the code I had been polishing — it was two environment/infra gaps.

**1. A missing `numpy` turned into "retired engine" skips.** `release.py` calls
`provenance.verdict()` to refuse songs rebuilt by the rejected Piper engine. That
module imports numpy. On a fresh pod numpy was absent, the import raised, and
`is_retired` **fails closed** — it prints "provenance check unavailable
(ModuleNotFoundError); skipping the song rather than risk the retired engine" and
skips *every* song 39-48. A whole day of the release rail was green (rc 0) and
uploaded nothing. Lesson: `provenance check unavailable` in the log is a broken
pod, not a verdict. Install numpy first.

**2. `release.short_files()` only lists hook cuts that are RELEASE ASSETS.** It
scans `_release_asset_names()` for `short-<mix>-h*<slug>.mp4`; a file sitting on
local disk is invisible unless its plain name matches. So a freshly rendered Short
is not plannable until `scripts/publish_media.py` pushes it to the `media-938`
release. That is the actual gap between "rendered" and "queued".
- `python3 scripts/publish_media.py --dry-run` then with no flags (idempotent,
  skips names already present). Needs `AX_GH_TOKEN`.
- Verified: after uploading 16 files for song 48, `release.py --plan --shorts`
  finally printed `SHORT 48-luai-mai-yut-v48`.

**Upload walls that are real, not bugs.** `release.py --next` refused with
"today's uploads are done: 2/2" — the cadence cap (`UPLOADS_PER_DAY=2`) on the
Pacific day, not a quota error. A `READ FAILED 403 ... exceeded your quota` line
right after it is the shared 10k API pool, and it is *separate* from the upload
cap; a live `yt_auth.get_videos` probe still answered 200, so always probe before
believing a 403 means the rail is dead.
