## What shipped
- `ops/fb_graph.py`: added `post_photo()` (`POST /{page}/photos`, multipart, stdlib
  only — urllib has no multipart writer so the body is assembled by hand) and
  `post_link()` (`POST /{page}/feed`). Both share the one System User token and
  the same "None = not configured" contract as `post_reel`.

- New captions: `photo_caption()` (cover art, distinct from the Reel caption) and
  `link_caption()` (Shopee card + mandatory ad disclosure).
- `--augment-formats`: idempotent in-place migration of the committed queue. Needed
  because a fresh pod has no `library/` and cannot rebuild the queue from disk.
  Ran it here: FB items 72 -> 102 (+25 photos, +5 links).
- Cadence: `MIN_GAP_SECONDS` 20min -> 1h; `FACEBOOK_DAILY_CAP` 2 -> 3 (unchanged
  TikTok 4); new `LINK_DAILY_CAP = 1`.
- Loop fix: a link item blocked by the link cap is *skipped*, not treated as a
  stop. Otherwise the rail posts nothing for a day while photos/Reels sit ready
  behind the blocked link. The top-level gate now checks base rules only.

## Session 2 — "อัพเดท งานแรก": release-engine fixes + ledger reconcile

K's instruction "อัพเดท งานแรก" = progress the first (FB) task's rail. The real
blocker turned out to be one layer down: the **release engine** was losing every
upload it made, so the whole channel (and therefore FB's content source) stalled.

### Root causes found and fixed (all in `music938-1/scripts/release.py`)
1. **Ledger loss (the big one).** `daily_release.py` wrote the ledger back to
   `main` only on `rc == 0`. A capped batch (rc 3) had just uploaded several
   videos, then returned *before* the write, so the ledger never learned about
   them. Next run re-planned the same items and re-uploaded. Live proof: the same
   affiliate card ("3 จุดที่ควรดู ก่อนซื้อหูฟังบลูทูธ") was on the channel **4×**
   while the ledger held **0** affiliate rows. Fixed by moving the write above the
   rc check; pinned in `test_daily_release_saves_ledger_on_early_stop`.
2. **`fetch_media` had no retry.** A single 504 from the release CDN escaped as a
   traceback and aborted the whole batch (run `42467399481` uploaded nothing).
   Now retries 3×, and the batch loop *skips* an rc-2 item instead of stopping.
3. **The CDN 504 itself.** `browser_download_url` 302-redirects to a separate CDN
   host that 504s under load. The API's `releases/assets/<id>` endpoint streams the
   same bytes, no redirect — measured **0.4s vs 10.9s**. `fetch_media` now prefers
   it (needs the asset id, so `_media_assets` carries it) and falls back to the
   browser URL. This is what makes the affiliate cards (the only Shopee link) land.
4. **Transient playlist insert.** A 409 SERVICE_UNAVAILABLE on
   `playlistItems.insert` lost the discovery row for an already-uploaded video;
   now retried (409/5xx only, a real 403 returns at once).
5. **`uploadLimitExceeded`** (YouTube's *channel-level* cap, separate from the
   API's 100/day `videos.insert` bucket) surfaced as a red run; now treated as
   day-done (rc 3) so the workflow stays green.

### Ledger reconciliation (`music938-1/scripts/reconcile_ledger.py`, new, idempotent)
Retired 6 rows whose videos were deleted in earlier cleanups (5 karaoke +
`zNqUTtCaYxY`), recorded the 2 surviving cards (`X3A5PMMNgfU`, `y-Y2DNmopHk`).
Without this the rail re-uploaded those cards every run.
