## The genart fail-open was the actual bug, not the three rows

`shard()` selected `local = [... (ART / w["png"]).exists()]` and, when that was
empty, returned **0**. So a manifest full of orphans reported success and the
rail committed it — which is exactly how "29 works, 2 existed nowhere" happened
on 2026-11-19. Two fixes, both needed:

- `shard()` now returns 1 if any row has no shard and no local file.
- `ax-genart.yml` dropped `|| echo "::warning::shard upload failed"`. A swallowed
  upload failure is what let the commit step publish the lie.

Both are pinned by checks in `test_genart_is_original_reproducible_print_art`.

## `--dry-run` must survive the hold

Adding the hold gate to `bank_publish.main()` broke
`test_clip_lane_is_its_own_job`, which drives `main()` with `--dry-run` to pin
the pending-selection logic. The gate was right to exist and wrong to fire
there: **the hold blocks uploads, not inspection.** A dry run uploads nothing,
and while the hold is on it is the only way to see the pipeline at all. So the
check is `if not a.dry_run:` — real runs refused at the door, dry runs allowed.

## Bank lane: the two halves disagreed about where a clip lives

`clip_lane.py` writes `library/bank/bank-<mix>-<slug>-<theme>.mp4` and uploads
it itself. But `pull_media.group_of()` had no `bank-` rule, so on a fresh pod
`library/bank` stayed empty and `bank_publish` had nothing — while the generic
`short-*` rule was busy filing a stray bank clip into `library/shorts/`, the
posting queue, where it needs a lyric file it does not have. That single missing
rule caused both the empty bank and the crosspost crash.

Fixed: a `bank-` rule in `group_of()` (matched before `short-`), and
`("bank", "bank-*.mp4")` in `publish_media.SOURCES`. The narrow pattern means
the row can never sweep up a Short.

## Session 2 (10:39) — the bed leak, found at the root

### The five "restored" masters were beds, and the proof is a correlation
Commit `0953067` ("real songs restored: five Flow renders replace the beds")
claimed five Flow renders. They were not: song-vs-karaoke correlation measured
on the shipped files:

| slug | corr(song, karaoke) |
| --- | --- |
| 28, 34, 37, 41, 43 | 0.9978 – 1.0000 |
| 07 (a real Flow song) | 0.7911 |

A bed's "karaoke" is the same synth re-encoded, so it correlates ~1.0 with its
own song. A sung song's instrumental cannot, so 0.79 is the healthy number.
`provenance.is_bed` (48 kHz Flow vs 44.1 kHz bed) was right all along.

**The renders are gone, not hidden.** All 32 masters share mtime
2026-11-21T10:48 — one bulk restore. Masters are gitignored
(`music938-1/library/songs/*.mp3`), so git could never bring them back, and the
restore commit touched only manifests and tests, never the audio. The release
still holds the 2026-11-18 bed (`song-28` = 5761611 B). Nothing on disk is
48 kHz for those five.

### The actual root cause: `compass.songs()` filtered genre but not beds
`compass.songs()` is documented as "the single enumeration every render lane
must use", and it applied only `genres.publishable()`. So **every** song-based
lane — short, mv, compilation, concert, bank, surreal, film — listed all four
active-genre beds (34/37/41/43). The bed guard existed only in `clip_lane` and
in `make_short.render()`, i.e. downstream of the enumeration. `--all` skipped
them, but any lane handed one slug rendered it.

Fixed in three places, all fail-closed:
- `compass.songs()` drops a bed (`provenance.is_bed`) as well as a parked genre.
- `compass.is_publishable()` now answers the bed question too, so the single-slug
  form cannot disagree with the list form.
- New `compass.require_publishable(slug)` raises; the four lanes that take a slug
  on argv (make_short, make_surreal_short, make_concert_short, make_film_video)
  call it. Their `--all` path already went through `compass.songs`.

### The honest catalogue is 9, not 13
Excluding the beds drops publishable from 13 to 9, below `MIN_TRACKS` 12 and
`MIN_VOLUME_TRACKS` 12. Both levers are therefore **dark**, and `build()` already
refuses below the floor (pinned). The two tests that read as failures were
reporting that truth. Rewrote both to assert the thing that is true at any
catalogue size — *the picker takes every eligible song* — and to name the dark
lever as a note, so the real defect (a picker that silently drops songs) still
fails the suite.

### `pull_media` clobbered the renders (the reason they are gone)
`main()` overwrote any local file whose size differed from the release. The
release is only refreshed when a rail uploads, so a render made after the last
upload exists nowhere else. Now: a differing non-empty local file is a
**conflict**, kept and reported; `--force` overwrites; `--strict` exits 3; the
download writes to `.part` then `replace()` so a cut transfer is never a file.
`publish_media` keeps the opposite asymmetry (local wins, asset replaced) —
that is correct and deliberate.

### Also fixed: photos bunched at the front of the crosspost queue
32 cover photos at a fixed `every=3` were all spent by item 138 of 279, leaving
140 items with none. `interleave(..., spread=True)` widens the stride to
`len(primary)//len(secondary)`; photos now span 9..266. Affiliate cards keep
their fixed early stride on purpose (revenue must land on day one).
