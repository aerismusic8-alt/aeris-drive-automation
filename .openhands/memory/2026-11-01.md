A fresh pod, so the repo was re-cloned and the toolchain rebuilt. Two of the four
music automations were red; the other two were green. The split was the clue.

### Root cause: an automation sandbox gets no user secrets as env vars

An **interactive** session is handed the user's secrets as environment variables.
An **automation** sandbox is not — it sees only the secrets it explicitly
selected. So every script that read `os.environ` directly worked when a human ran
it and failed under cron:

- `AX Music Marketing Daily` died with `missing secret YT_CLIENT_ID`
  (`market.py`).
- `AX Music Daily Release` never uploaded for the same reason.
- The one rail that worked, `AX YouTube Activity Monitor`, already had a
  `get_secret()` fallback: read the env, else
  `GET {AGENT_SERVER_URL}/api/settings/secrets/{name}` (or the cloud path
  `/api/v1/sandboxes/{SANDBOX_ID}/settings/secrets/{name}`) with
  `X-Session-API-Key`. That is the route that works in a sandbox — **not** the
  old "secrets are BLOCKED" dead end.

Fix: `ops/ax_secrets.py` (`get_secret`/`require`), used by `yt_auth.access_token`,
`market.secret` and `ar_promo_site.secret`. Commit `0245f45`, pinned by
`test_automation_secret_fallback`. The plugin fetches the repo tarball at run
time, so a push is enough to update the automation.

## Session 3: the marketing loop was measuring an empty channel

Found while sanity-checking the daily report against the live channel. The report
said **1 sub, 20 videos**; the API said **3 subs, 21 videos**. The report had also

### Root cause: `market.py --root` meant two different things

`market.py` read the ledger at `<root>/work/release-state.json`. Every sibling
script — `daily_release.py`, `pending_replacements.py` — takes `--root` as the
**repo root** and then does `root / "music938-1"`. The `market-daily` plugin calls

`<repo>/work/release-state.json`, which does not exist; `released_ids()` returned
`[]`; the report tracked **zero** videos and the run still exited `0`.

That is why the bug hid: the automation was **green every day** while producing an
empty report, and market-daily's own test only checked that the plugin passes
`--root`, never that the flag means the same thing on both sides.

Fix: `resolve_root(base)` returns `base / "music938-1"` when that dir exists, else
`base`, so both callers work. Pinned by `test_market_root_resolution` (329 tests).
The corrected run reports 13 tracked videos and `ผู้ติดตาม 3 (+2)`.
