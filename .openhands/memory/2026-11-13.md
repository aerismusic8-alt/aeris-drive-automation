## What shipped
`music938-1/scripts/make_film_video.py` — cuts a real film from the Internet
Archive and matches it to the song three ways:
- **casting by mood**: the lyric header `# MOOD:` picks the film (`film_for_mood`).
  epic → the rock'n'roll film, sad → the noir film.
- **cut by section**: `window_sections()` reads the song's sections, then
  `plan_by_section()` cuts a chorus at ~2× the base beat and a verse ~1.4× slower.
  Verified: chorus 21–23 cuts/s vs verse 4–6 cuts/s (4–5× faster).
- **grade by section**: `section_grade(mood, energy)` lifts the hook
  (`brightness=0.03`) and pulls the verse down (`brightness=-0.03`).
- footage is chosen by `clip_stats()` energy (bright + motion, dark frames
  rejected), so the chorus gets the film's active moments.
- the film's own audio is dropped (`-an`) so no third-party score can be claimed.

Rendered the full song `24-yut-mai-yom` (rock, epic, Em, 160 bpm, 212.5 s) from
**Rock, Rock, Rock! (1956)** — colour, `licenseurl:

The B&W boxing film (`They Made Me a Criminal`, 1939) was the earlier cut.

## Live view instead of noVNC — built and measured (2026-11-13)
K asked whether something better than VNC exists. Answer: yes, and one variant is
already built here and verified. `ops/live_view.py` + `ops/live_view_server.py`.

- **The X screen does not repaint on this sandbox.** `scrot` of `:99` is byte-identical
  across 1.5-2 s while the browser is active, so **noVNC shows a frozen picture** —
  the window manager frame is 1400x860 and mapped, yet nothing is composited to it.
  This is why noVNC looks dead; it is not the VNC transport.
- **`Page.startScreencast` yields exactly one frame and stalls here.** Measured 0-1
  frames in 6-10 s on both the main browser and a second Chromium launched with
  `--disable-gpu`. Do not build on it in this environment.
- **`Page.captureScreenshot` is live and fast.** It reflects a DOM change within a
  frame, ~85 ms latency, ~12 fps sustained, ~77 KB/frame at quality 50. This is the
  working transport.
- **Two `recv()` calls on one CDP websocket corrupt the stream.** A background reader
  thread plus a request waiter deadlocked the server (frames arrived on `/frame` but
  never on the WebSocket). The transport is now synchronous, one `_call()` at a time
  under a lock.
- **MJPEG over plain HTTP beats a binary WebSocket** for this: an `<img>` renders it
  with zero client code, and it survives a stall. Measured ~2.7 fps through the
  proxy at 52 KB/frame (the 0.08 s sleep dominates, not capture).
- **Control works end to end.** `Input.insertText` / `dispatchMouseEvent` via
  `POST /input` typed Thai into a page and the value read back identical; taps map
  from frame-normalised (u,v) to page CSS pixels.
- Run it: `python3 ops/live_view_server.py --port 12001 --serve-dir /tmp/serve`
  (12001 is the reachable port; `--serve-dir` keeps serving screenshots and the
  `repo.bundle` that `push-via-pc1.sh` fetches). Endpoints `/`, `/mjpeg`, `/frame`,
  `/tabs`, `/health`, `POST /watch`, `POST /input`.
- Other options and why they are not the move here: **KasmVNC** is not in the Debian
  repo (`not-in-repo`) and its win over x11vnc is image encoding, which does not fix
  a renderer that never repaints; **Selkies / neko** need a GPU and a Docker daemon,
  and Docker is installed but the service is inactive; **xpra** has no apt candidate;
  **Guacamole** needs an RDP/SSH endpoint, i.e. a second machine. The cheapest fix is
  the one that does not ship the X screen at all.
