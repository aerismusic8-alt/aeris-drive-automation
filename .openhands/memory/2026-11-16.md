## The real gap was never the tool — it was the wiring
`make_film_video.py` (archive.org public-domain film cut on the song's sections)
and `make_music_video.py` already build **real music videos** (film-24, mv-01,
film-26). They were **never published**: `release.py plan()` only ever scheduled
`library/karaoke/song-<slug>.mp4` (a lyric render = a still cover), so the daily
rail shipped stills under song titles. That is exactly what K scrolls past.

### Fix (commit `52c5182b6b`, pushed to main)
- `release.py`: `mv_files(slug)` / `has_mv(slug)` read the MV from the media
  release asset list (or disk) — `film-<slug>[-full].mp4` sorts ahead of
  `mv-<slug>[-full].mp4`; `-hook`/`-vertical` cuts are excluded (they are the
  Shorts, not the long-form release). `plan()` schedules the MV as the
  `kind=song` item and falls back to the lyric render only when none exists.
- `describe()`: an MV release gets a `มิวสิควีดีโอ` marker in the title via the
  new `mv_title()` — it **keeps the search intent** and the 60-char bound (a
  first cut used the tagline and dropped the intent; the
  `test_song_title_search_intent` suite caught it) — plus a `🎬` line in the
  description.
- `publish_media.py`: `library/musicvideo/*.mp4` now rides the durable
  `media-938` release, so the ubuntu release runner (fresh checkout) can pull the
  MV it publishes. Uploaded film-24, film-26, mv-01 x2 (404.7 MB).

  render); added, same reason as musicvideo/shorts.

  ordering, and the plan wiring. Full suite **2456 passed, 0 failed**.

## YouTube upload cap (reconfirmed 2026-11-16)
`videos.insert` -> HTTP 400 `uploadLimitExceeded` on ch3 even though ch3 had only
1 upload today. It is a **per-channel count of new videos/day** (unverified-channel
territory), independent of the shared API quota pool (which resets 08:00 UTC).
It clears over **hours**, and a burst tends to *extend* it. `film-26` is built,
verified (3:57, 1920x1080, mean YAVG 2.9) and queued; a gentle 45-min retry loop
(`/tmp/mvpub/retry_mv.sh`) will land it, and the daily rail now carries it too.
A preview is served on the pod's work-2 URL for K to watch meanwhile (dies on
recycle — the link is not a delivery channel).

Lesson: `film_for_mood` returns the *first* film whose `moods` list contains the
mood, so list order decides. A film whose mood word matches but whose *meaning*
does not is a silent mismatch — check the film a mood actually casts, not just
that the word is in the list.

## MV watch pages now auto-publish (2026-11-16)
The publisher `ops/mv_page.py` only worked on the pod that built the film — it read
the MV from a local `library/musicvideo/` and died on a fresh pod. Made it reusable
for **every** song and wired an operator-free rail.

- `release_mv_assets()` reads the `media-938` release list, so a fresh pod (empty
  `library/`) fetches the film it needs (`fetch_asset`, API asset URL then browser
  URL, 3 tries). `film_asset()` now falls back to the release. `--all` publishes a
  page for every long-form MV; an existing page is **skipped** so a daily run only
  re-encodes when a new MV shipped. `--force` overrides.
- Env overrides `MV_PAGES_DIR` (the Pages checkout) and `MV_SOURCE_ROOT` (the
  `music938-1` tree) let the Pages repo's own workflow drive the same script.
- **The rail is a workflow in the Pages repo itself**:
  `.github/workflows/ax-mv-pages.yml` in `site-aeris-music` (cron `40 9,15,21 * * *`
  + dispatch). It checks out the public music repo, installs ffmpeg + numpy + pillow
  (all the publisher needs), and runs `mv_page.py --all` with the Pages repo's own
  `GITHUB_TOKEN` — so **no cross-repo secret is required**. This was the blocker:
  the main repo has no `AERIS_GH_APP_*` secrets and `GITHUB_TOKEN` is scoped to one
  repo, so a cross-repo push had no token. Running the publisher *inside* the Pages
  repo sidesteps that entirely.
- A workflow file needs the **`workflow` scope** to push; the App token lacks it.
  Mint the classic token from the vault: `ax_vault.kv_get(ax_vault.ensure_anchor(),
  "axsecrets:gh-workflow-token")` (needs `OPENHANDS_API_KEY` set, else the anchor
  call 401s). Pushed `site-aeris-music` commit `1361807`.
- Verified from a **fresh clone** (simulated CI): `song_meta` reads the lyric header,
  `film_asset` fetches `mv-01-...-full.mp4` from the release, and the page renders —
  with only numpy + pillow + ffmpeg installed. `--all --dry-run` wrote all 3 pages.
- Tests: `test_mv_page` gained 6 checks (`_is_mv` recognises a long-form MV and
  rejects `-hook`/`-vertical` Short cuts; `slug_from_asset` recovers the slug from
  both shapes). Suite **2476 passed, 0 failed**; memory guard exit 0.
