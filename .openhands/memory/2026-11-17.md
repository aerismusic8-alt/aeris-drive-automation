  non-zero** on a fail, so a below-floor clip cannot be a finished artifact.

  clip to prove the gate rejects it (wrong size / audio / frozen). Suite 2514/0.

## Thumbnail floor: 20 fails -> 0, and why they split into two classes
The clip floor was already done; the thumbnail floor (ops/thumb_standard.py, K
2026-11-17 "แม้กระทั่ง thumbnail ก็ต้องได้มาตรฐาน 10/10") rejected 20 of 203.
- **Dark Short frames (12).** A Short's own frame is dark BY CONSTRUCTION: a
  blurred, scrimmed copy of the cover fills it. A plain `-frames:v 1` grab
  measured mean luma ~18 and 0% bright title, so the floor read "no title" — the
  thumbnail was faithful, the *grab* was the defect. Fix: lift the grab in
  make_short.thumb_for with `eq=gamma=1.6,unsharp=5:5:0.8` (measured rng 51->67,
  detail 0.22%, bright 0.11%). Verified the chain keeps all 28 already-good clip
  thumbs passing, so it is applied unconditionally, not conditionally.
- **Flat surreal posters (5).** The exhibit lane paints the cover through a
  recipe (melt/wave/ghost); the clip itself measures rng 33 at every frame, so the
  poster is faithful to flat art. Lifted the *poster* with
  `eq=contrast=1.7:brightness=-0.08:saturation=1.1`. (contrast=2.0 clears range
  but overshoots the 45% bright cap; gamma alone does not clear range.)
- **Oversized PNG (1).** 1080x1920 over 2 MB -> re-saved optimized RGB (1.7 MB).
- Two "fails" were square 1280x1280 covers = source art for animated lanes, never
  a YouTube thumbnail; the aspect rule does not apply. Not real failures.
Lesson: when the thumbnail floor fails, first ask whether the *grab* is faithful
or the *source* is flat — a dark Short grab and a flat poster need different fixes.
Publish route: `publish_media.py --only thumbs` replaces a changed asset in place
(deletes then re-uploads), so the fix is durable on a fresh pod only after this.

## Quota root cause found — measurement is now quota-free (2026-11-17 11:44Z)

The shared 10,000-unit/day YouTube pool (every endpoint except `videos.insert` and
`search.list`, which have their own 100/day buckets — confirmed in the official
quota-cost doc) is drained by **`live_audit.py --repair`**, which the dashboard runs
**three times a day** (`'30 8,14,20 * * *'`). Each run repairs up to `MAX_REPAIRS=50`
videos, and one `videos.update` is **50 units** -> up to **2,500 units/run, ~7,500/day**,
and it recorded **nothing** to `ops/yt_quota.py`. The ledger showed only 0-300 units/day
(`thumbnails.set` + `playlistItems.insert` from the release), so the pool looked idle
while it was being emptied — which is why uploads shipped thumbnail-less and the
measurement rail (`videos.list`) went blind (403 -> stale snapshot).

Fixes shipped:

- **Measurement is no longer blind.** `report.youtube_stats()` now falls back to
  `ops/yt_public_scan.channel_header(handle)`, a **zero-quota** read of subs / videos /
  total views off the public channel page (`/videos` metadata rows + `/about`
  `viewCountText`). Order: Data API -> public page -> last snapshot. Verified:
  subs=8, videos=82, views=2096, all read with no token.
- **The repair loop can no longer starve the release.** `live_audit --repair` now
  checks `yt_quota.remaining() < QUOTA_FLOOR (1500)` before each write, records each
  `videos.update` in the ledger, and `yt_quota.commit()`s the spend. The dashboard's
  audit step gets `AX_GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` so the commit works
  (the Contents API is the single writer — do NOT also `git add` the ledger file,
  or the rebase conflicts with the API commit).
- `yt_auth.access_token` raises `SystemExit` (a BaseException), so the fallback had to
  catch `(Exception, SystemExit)`. Same trap as `ax_vault.ensure_anchor()`.

Workflow files need the `workflow` scope: `AX_GH_TOKEN` here is `gist,read:org,repo`
(no workflow). Read the classic PAT from the vault — `ax_vault.kv_get(anchor,
"axsecrets:gh-workflow-token")` returns a **dict** `{token, login, scopes, note}`,
not a string (scopes `repo,workflow`). Pass `OPENHANDS_API_KEY` in the env.
