## Round 2 — k-free audit was stale after fb_relogin.py landed

**Error found:** `ops/k_free_status.py` still classified the Facebook browser
fallback as "needs K repeatedly", so `--check` exited 1 and named a rail that no
longer needs K (AR revives it from the vault). TikTok genuinely still needs K (no
TikTok password in the vault).

**Meeting held:** `ops/consult.py` on the classification question. Quorum PASS
(duck + pollinations). Both ranked: **1. new kind `browser-revivable`**, 2. K-free,
3. oneshot. Consensus: revivable-from-vault ≠ K-free (a checkpoint could still
need a human) but ≠ recurring either; `--check` must fail only on genuinely
recurring rails.

**Fix shipped:** `revivable_by` column in the RAILS table; `_vault_has()` checks
the KV key's *presence* only (never reads the value); new `AGENT` class + JSON
`revivable`/`needs_k_revivable`; `--check` ignores revivable rails. Facebook →
AGENT, TikTok → NEEDS K. Extended `test_k_free_status` (19 checks, vault stubbed)
and the runbook. Suite: 1743 pass / 5 environmental. Pushed `4916c7f`.

**Lesson:** a capability upgrade must be reflected in the audit that measures it,
or the audit lies. `--check` is only trustworthy if it distinguishes "K needed
again" from "agent can heal itself".
